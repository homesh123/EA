🌊 Streaming data: Kafka and real-time pipelines

EnglishHinglish

🏠 Real-life example

Batch processing is like reading the morning newspaper: yesterday's news, all at once. Streaming is like a live cricket score app: every ball updates instantly. Fraud detection, live delivery tracking and real-time recommendations need the live-score approach.

💡 In simple words

In streaming, events (a click, a payment, a GPS ping) flow continuously. Apache Kafka is the standard backbone: producers write events to topics, Kafka stores them durably in order, and consumers read them at their own pace. Stream processors (Spark Structured Streaming, Flink) compute things on the fly, such as rolling counts and features for fraud models. Streaming adds complexity: late or duplicate events, ordering and exactly-once guarantees. Start with batch, and add streaming only where freshness truly matters.

🔑 Key terms

Event
A single fact that happened at a time, e.g. 'payment of ₹499 at 10:02'.
Topic
A named stream of events in Kafka.
Consumer
A service that reads and processes events from a topic.

👀 See it in action

text
UPI app ──payment event──▶ Kafka topic 'payments'
                                  │
          ┌───────────────────────┼───────────────────────┐
   fraud scorer            live dashboard          warehouse loader
   (reacts in < 1 s)       (updates per second)    (hourly batch)

One stream, many independent consumers, each at its own speed.

✅ Quick check

Which use case most needs streaming instead of a nightly batch?

  1. Yearly HR summary
  2. Blocking a fraudulent payment as it happens
  3. Monthly finance report
Show answer

B. Blocking a fraudulent payment as it happens: Fraud must be stopped in seconds. A report tomorrow is too late.

📌 Remember

Batch = periodic, simpler. Streaming = real-time, more complex. Use it when seconds matter.
